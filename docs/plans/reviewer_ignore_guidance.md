# `reviewerAgent-ignore.md` — declarative skim-guidance for data-heavy commits

## Why

Some repositories produce commits with hundreds of data files (`.jsonl` rows, `.csv` outputs,
scraped `.txt` captures, generated JSON manifests). Reviewing these row-by-row is not meaningful
— the reviewer cannot judge whether an individual record is correct, only the source-of-truth
can. Meanwhile these files bloat the audit:

- On the healthy path, codex runs `git diff --cached` itself and spends reasoning time on paths
  that add no signal.
- On the **retry** path (a re-audit after rejection), the hook proactively **inlines** deltas
  for each changed path via `_inline_deltas` (`reviewer_prompts.py:921`), consuming prompt tokens
  before codex sees anything.

Live evidence: `reviewed-project/research_out` has hit total-cap timeouts on large commits (staged
2400 s cap; 12:58 today, exit=124, 1003 files / 464,550 lines). The current dodges are "raise
the total cap" or "split the commit," both of which push effort onto the operator without
addressing the root cause.

## Design principles the mechanism must preserve

1. **Fail-closed on malformation.** The gate still runs on every commit. Any parse error in
   the ignore file blocks the commit with a clear reason. A **missing** ignore file is NOT an
   error — it's normal, meaning "no exclusions" and matches today's behavior; only a *present
   but malformed* file is fail-closed.
2. **No per-commit escape hatch.** No commit-message tag, no `--no-verify` equivalent, no
   size-based auto-skip. The developer agent cannot bypass the gate by manipulating the commit
   itself.
3. **Exclusion config is itself under review — mandatorily.** The ignore file is a normal
   repo file. Any change to it appears in a commit's diff and gets fully reviewed. A developer
   agent that adds `src/**` to the ignore file has to get that change past the reviewer
   first. The parser hard-codes an **exemption** for `reviewerAgent-ignore.md` itself: the
   filter *always* excludes its own path from the matched-paths set before returning, so no
   pattern (even `**` or `*.md`) can hide the ignore file's own diff.
4. **Delayed application — new ignore rules do NOT apply to the commit that introduces them.**
   The self-exemption alone doesn't prevent a "trojan commit" where the developer agent
   simultaneously (a) changes `reviewerAgent-ignore.md` to add `src/**` and includes prose
   telling the reviewer to skim aggressively, and (b) stages malicious changes under
   `src/**` in the *same* commit. If the new patterns applied immediately, the reviewer
   would evaluate the malicious changes under the more-permissive new rules.
   **Rule:** when the ignore file itself appears in the staged diff (i.e. is one of the
   changed paths), the audit uses the **PREVIOUS** version of the ignore file (from `HEAD`,
   via `git show HEAD:reviewerAgent-ignore.md`) to filter, NOT the staged version. New
   patterns only take effect on the *next* commit after the ignore-file change is landed.
   Absent ignore file at HEAD (first-time introduction) → no filter applies for that commit;
   every staged path is fully reviewed. This is symmetric with the codex-side prompt:
   Channel A also shows the *previous* file's prose (or none, on first introduction) when
   the ignore file is being changed, so codex sees the rules that are in effect for THIS
   audit, not the ones the commit proposes.
5. **Codex is *told* what was skimmed, not lied to.** The prompt names the ignore file's
   contents and clarifies what codex can and cannot judge from skimmed paths.
6. **Codex retains authority to fetch anything.** The ignore file is guidance, not enforcement
   on codex. If a summarised path looks suspicious, codex can `git diff --cached -- <path>`
   itself and audit.

## Shape

### 1. The ignore file

**Name:** `reviewerAgent-ignore.md` at the target repository's root, alongside
`reviewerAgent.md`. Optional — a missing file means "no exclusions," which is today's behavior.

**Format:** free-form markdown for human context, plus one or more fenced code blocks tagged
`reviewer-ignore` carrying the machine-readable patterns:

````markdown
# What to skim on this repository's commits

The `data/**/*.jsonl` files are auto-generated by the mixNN pipeline. Row-level content
correctness is verified upstream by the pipeline's own tests; the reviewer should not attempt
to judge individual records. Structural changes (header/schema) still matter — flag anything
unexpected.

```reviewer-ignore
data/**/*.jsonl
research_v2/**/results/**
sources/text/*.txt
sources/text/*.html
```

Binary manifests and captured PDFs are also opaque:

```reviewer-ignore
**/*.pdf
**/*.zip
**/*.sqlite
```
````

The fence tag is **`reviewer-ignore`** (not `gitignore`, since these patterns are not fed to
git and semantic drift would confuse). Any other fenced language is ignored by the parser.

**Pattern syntax (v1, minimal in-repo matcher — NOT full pathspec/gitignore parity):**
Patterns are matched against **repository-relative POSIX paths** of staged files. Supported:

- `*` — matches any run of characters within a single path segment (no `/`).
- `**` — matches zero or more full path segments (e.g. `data/**/results` matches
  `data/results` and `data/x/y/results`). Only recognised in one of these positions:
  as a standalone segment (`a/**/b`), as a leading segment (`**/a`), or as a trailing
  segment (`a/**`). Embedded uses like `**foo` are not recognised in v1.
- `?` — matches exactly one character within a single path segment.
- `[abc]` / `[a-z]` — character class within a single path segment.
- Leading `/` — anchors the pattern to the repository root
  (`/data/*.jsonl` matches `data/x.jsonl` but not `subdir/data/x.jsonl`).
  Without a leading `/`, patterns match anywhere in the path.
- Trailing `/` — pattern only matches directories (rare in v1 since we match files, but
  parsed for future-proofing).
- Lines starting with `#` and blank lines are ignored inside fenced blocks.

Explicitly NOT supported in v1:

- `!` negation (whitelist patterns) — every listed pattern is unconditionally an exclusion.
- Escape sequences like `\ ` for literal spaces or `\!` for literal `!`.
- Case-insensitive matching (paths are matched case-sensitively).

Any unsupported syntax → parser returns a non-None error with the pattern and reason
("unsupported syntax: `\\ `"). Fail-closed on parse errors, per Principle 1. The parser's
docstring and README both document this restricted subset explicitly so operators know what
to write — the fenced-block tag is deliberately `reviewer-ignore` (not `gitignore`) to make
this narrower semantics obvious.

### 2. Two delivery channels

The hook is responsible for delivering the exclusion information through **both** channels the
audit sees content on. Filtering one without the other leaves a leak.

**Channel A — the codex prompt (healthy path and retry).** The **full markdown file contents**
(prose + fenced blocks) are prepended to every commit-audit prompt, in a labelled block that
follows the standing brief. Codex reads the prose rationale AND the patterns, and can
self-regulate on its own `git diff --cached` runs. The prompt block includes a short
directive:

> The following block is the operator's `reviewerAgent-ignore.md` for this repository — it
> names paths whose content is auto-generated data. You may judge: whether changes to those
> paths match the commit's stated intent; whether their schema (header line / first-record
> structure) has changed unexpectedly; whether their presence, naming, or location is
> appropriate. You may **not** judge the correctness of individual records. If a change on a
> skimmed path looks suspicious, run `git diff --cached -- <path>` yourself and audit; you have
> not been forbidden anything.

Missing file = the block is absent, exactly today's behavior. Codex is never told a file exists
that doesn't.

**Channel B — the hook's `_inline_deltas` (codex retry path only in v1).** The hook loads
the ignore file at commit-audit time, parses the `reviewer-ignore`-tagged fenced blocks into
a matcher, and applies it to `_delta_candidates` (`reviewer_prompts.py:963`). Matched paths
are removed from the candidate set before `_inline_deltas` runs. Result: the codex retry
prompt never carries inlined diff text for skimmed paths.

**Scope: codex only in v1.** The other backends deliver the diff through different code
paths that this filter does NOT reach:

- **Claude** receives the full staged diff inlined in the commit prompt
  (`commit_hook.py:126-169`). The filter on `_delta_candidates` does not touch that path.
- **Pi** fetches the full staged diff itself via its git tool (`reviewer_prompts.py:111-114`),
  so no hook-side filter can withhold content it fetches on demand.

For both backends, Channel A (the ignore file's prose + patterns in the prompt) still gives
them guidance the same way it does for codex, but Channel B's byte-level exclusion is
codex-specific. Extending Channel B to Claude requires modifying the inline-diff
construction; extending it to Pi requires a mechanism to communicate the exclusions through
its git tool. Both are out of scope for v1 — separate follow-up plans, one per backend.

The v1 promise, restated precisely: **on the codex backend**, an ignore pattern removes the
matching file's diff from both the codex prompt (via Channel A guidance) and the retry
inline set (via Channel B filter). On pi and claude, only Channel A applies.

### 3. Fail-closed on parse error

The parser can fail two ways:
- The file exists but cannot be decoded as UTF-8 → block the commit with the operator-visible
  reason `"reviewerAgent-ignore.md is not valid UTF-8 (line N)"`.
- A fenced-block pattern is malformed → block with `"reviewerAgent-ignore.md fenced block at
  line N: invalid pattern '<pattern>' (<reason>)"`.

Both failures are surfaced through the same `stderr_tail` channel any other reviewer failure
uses, so the operator can see and fix without inspecting logs.

**Not fail-closed:** the *absence* of `reviewerAgent-ignore.md` is normal and never blocks.
Only its presence-plus-malformation is fail-closed.

### 4. Audit-record visibility

The audit record and reviewer log line gain two new fields:

- `ignore_matched_files`: integer count of staged files that matched an ignore pattern.
- `ignore_matched_lines`: integer sum of `+X/−Y` across matched files.

So an operator scanning the log can see the exclusion mechanism working:

```
staged_files=1003 staged_lines=464550 ignore_matched_files=987 ignore_matched_lines=459812 …
```

Both fields are `0` when the file is absent, and `0` when the file exists but no staged path
matches (a small commit that doesn't touch data).

## Files that must change

### Code

- `reviewer_prompts.py`:
  - New helper `parse_reviewer_ignore(proj, staged_paths) -> (matcher, prose, err)`:
    - **Effective source (used for filtering + prose):** determined by whether
      `reviewerAgent-ignore.md` is in `staged_paths`:
      - If **NOT staged** (unchanged in this commit): read from the git index
        (`git show :reviewerAgent-ignore.md`) — the currently-committed version.
      - If **staged** (this commit changes it): read from `HEAD`
        (`git show HEAD:reviewerAgent-ignore.md`) — the *previous* version.
        This implements Principle 4 (delayed application).
    - **Validation of the staged candidate (parse-error fail-closed):** when the ignore file
      is in `staged_paths`, ALSO load and parse the staged version
      (`git show :reviewerAgent-ignore.md`). Parse errors on the staged version block the
      commit even though the staged version is not applied to this audit. Rationale: an
      operator introducing or modifying the ignore file should learn *at commit time* that
      their new content is malformed, not on the next commit when the file's changes take
      effect. The gate is fail-closed on any parseable-error (staged or effective).
    - In all cases, the file is loaded from a git object, NOT the working tree. Working-tree
      content cannot influence filtering — that would let an unstaged/untracked file affect
      staged deltas.
    - Extracts `reviewer-ignore` fenced blocks, compiles a matcher, returns the effective
      version's full markdown text as `prose` for Channel A.
    - `err` is non-None on parse failure of either the effective ignore file OR the staged
      candidate when the file is in `staged_paths`.
    - Absence at the resolved effective ref (`git show` exits non-zero because the path
      isn't tracked there) → empty matcher, empty prose, no error. Includes the
      first-time-introduction case (staged now, absent at HEAD): the staged candidate is
      still validated for parse errors, but the effective matcher is empty.
  - `_delta_candidates` (or its immediate caller): filter out paths matched by the parser
    before returning.
  - Commit-prompt composer: append the labelled `reviewerAgent-ignore.md` block after the
    standing brief when the file exists.
- `commit_hook.py`:
  - On `parse_reviewer_ignore` error, exit fail-closed with the reason in `stderr_tail`,
    without invoking codex.
- `reviewer_audit.py`:
  - Record `ignore_matched_files` and `ignore_matched_lines` on the audit record; carry through
    to the log line format.

### Dependencies

- **No external dependency.** The runtime has no formal deps declaration, and the plugin
  must work on operators' machines without an install step. A ~100-line in-repo
  `reviewer_ignore_match.py` module implements the subset of gitignore-style glob semantics
  the ignore file needs: `*`, `**`, `?`, `[...]`, leading `/`, trailing `/`, and `#`
  comments. Explicit non-support (documented in the parser's docstring and in README):
  `!` negation, `**` at arbitrary depth beyond the standard prefix/suffix forms. This is a
  smaller surface than `pathspec` but covers every pattern shape the design calls for.

### Docs

- `README.md`:
  - New section under "Claude Code commands" or a dedicated subsection describing
    `reviewerAgent-ignore.md`: what it does, when to use it, the two-channel guarantee, the
    fenced-block format, the fail-closed-on-parse-error semantics.
  - Command-line examples of writing a first ignore file.
- `AGENT_INSTALL.md`:
  - Optional mention that operators of data-heavy repos may want to add
    `reviewerAgent-ignore.md` after Step 5.
- `CHANGELOG.md`: new "Added" entry.

### Not touched

- No hook or hook-registration changes.
- No plugin manifest changes.
- No changes to `stop_hook.py`, `askq_answer_hook.py`, `session_start_hook.py`.
- **Pi and claude backends: Channel A (in-prompt guidance) applies as it does for codex, but
  Channel B (byte-level exclusion of diff content) does NOT in v1.** Claude gets the full
  diff inline via `commit_hook.py:126-169`; pi fetches the diff itself via
  `reviewer_prompts.py:111-114`. Extending Channel B to those backends is separate follow-up
  work per backend, out of scope for v1.

## Tests (red before green, per TDD)

**Parser tests** (new `tests/test_reviewer_ignore.py`):
- Missing file (not in the index) → returns empty matcher, empty prose, no error.
- **Working-tree-only file (unstaged, present on disk) → returns empty matcher, empty prose,
  no error.** Proves working-tree content cannot control filtering.
- **Untracked working-tree file (present on disk, never `git add`ed) → returns empty matcher,
  empty prose, no error.** Same guarantee.
- **Staged file matches the index; a modified working-tree copy with different patterns is
  ignored** — parser sees the *staged* patterns, not the working-tree ones.
- Well-formed staged file with one fenced block → matcher accepts `data/x.jsonl`, rejects
  `src/x.py`.
- Multiple fenced blocks → union of patterns.
- Non-`reviewer-ignore` fenced blocks (e.g. `python`) are ignored.
- Malformed pattern → returns non-None error with pattern text and line number.
- Non-UTF-8 file → returns non-None error.
- Empty file → returns empty matcher, no error.
- **Self-exemption: a pattern that would otherwise match `reviewerAgent-ignore.md`
  (e.g. `*.md`, `**`, `reviewerAgent-ignore.md`) does NOT cause the matcher to include the
  ignore file's own path in the matched set.** Verified by feeding
  `reviewerAgent-ignore.md` as an input path and asserting `matcher.matches(path) == False`.
- **Delayed application — ignore file NOT in staged_paths → read from index (`:`).** With a
  committed ignore file matching `data/**`, an audit whose staged paths don't include
  `reviewerAgent-ignore.md` uses those patterns.
- **Delayed application — ignore file IN staged_paths → read from HEAD.** With `HEAD`'s
  ignore file matching `data/**` and the staged version *modified* to also match `src/**`,
  an audit whose staged paths include `reviewerAgent-ignore.md` AND `src/foo.py` sees
  `src/foo.py` as full-review (HEAD patterns are used, not staged).
- **Delayed application — first-time introduction.** With no ignore file at HEAD and a
  staged ignore file matching `src/**`, an audit whose staged paths include the new
  ignore file AND `src/foo.py` sees `src/foo.py` as full-review (no filter applies because
  HEAD has none). New patterns take effect only on the *next* commit.
- **Delayed application — Channel A prose comes from HEAD, not staged.** With `HEAD`'s
  ignore file containing prose `"OLD RULES"` and the staged version containing
  `"NEW-TROJAN PROSE"`, an audit whose staged paths include `reviewerAgent-ignore.md`
  produces a commit prompt whose Channel A block contains `"OLD RULES"` and NOT
  `"NEW-TROJAN PROSE"`. This guards against a modified ignore file supplying attacker-crafted
  prose ("don't judge individual records") that could weaken this audit; the new prose only
  reaches codex on the *next* audit.
- **Delayed application — Channel A on first-time introduction is empty.** With no ignore
  file at HEAD and a staged one being introduced, the Channel A prompt block is absent
  (matching the "no ignore file present" baseline for this audit).
- **Staged validation — malformed newly-introduced ignore file fails closed.** With no
  ignore file at HEAD and a staged, malformed one (bad UTF-8 or invalid pattern), the audit
  fails closed with the parse-error reason, even though HEAD has no file for effective use.
- **Staged validation — malformed modification of an existing ignore file fails closed.**
  With a well-formed ignore file at HEAD and a malformed staged version, the audit fails
  closed with the parse-error reason for the *staged* content (not HEAD's, which parses
  fine).

**Channel A tests** (extend `tests/test_commit_hook.py` or new `tests/test_ignore_prompt.py`):
- Ignore file present → commit prompt contains a labelled block with the file's full
  markdown contents after the standing brief.
- Ignore file absent → prompt contains no ignore block (exactly today's shape).

**Channel B tests** (extend `tests/test_reviewer_lib.py` or the file that covers
`_delta_candidates`):
- With no ignore file, `_delta_candidates` returns all changed paths (today's behavior).
- With an ignore file matching some paths, those paths are absent from the returned set.
- Malformed ignore file → the hook fails closed (exit != 0, empty verdict, reason in stderr).

**Audit-record tests**:
- `ignore_matched_files` and `ignore_matched_lines` are `0` when the file is absent.
- Both fields report the expected counts when the file matches some staged paths.

**End-to-end** (extend `tests/test_commit_hook.py`):
- A commit with a mix of data-file and code-file changes, with an ignore file matching the
  data files, produces a prompt where Channel A carries the ignore block and Channel B
  omits the data-file deltas from the retry inline set.

## Non-goals

- **Computing summaries for excluded files.** Codex fetches the diff itself on the healthy
  path; the ignore file's prose + the labelled prompt block are enough guidance. If codex
  wants schema/header info it can `git diff --cached -- <path>` on demand. No pre-computed
  summary block in v1.
- **Per-pattern tiering** (my earlier proposal). Ignore or don't — no `tier=N` per pattern in
  v1. Can be added later without breaking the format (fenced-block extension).
- **Whitelist patterns** (gitignore-style `!pattern`). Not in v1; every listed pattern is
  ignored. Whitelisting can be added later.
- **Global config.** No `~/.claude/reviewer-agent/reviewerAgent-ignore.md`. Per-repo only,
  because the "what's data vs code" decision is repo-scoped.
- **Any change to the pi or claude backend's byte-level diff delivery.** They receive
  Channel A guidance the same way codex does, but their diff-delivery paths
  (`commit_hook.py:126-169` for claude, `reviewer_prompts.py:111-114` for pi) are not
  filtered in v1. See the "Scope: codex only in v1" paragraph above.
- **Any change to the standing brief (`reviewerAgent.md`).** The ignore file is a separate
  concern with its own file.

## Open questions

- **`pathspec` availability.** The runtime doesn't have a formal deps declaration today, and
  the plugin has to work on operators' machines. If `pathspec` isn't importable, options:
  (i) bundle it in the plugin, (ii) implement a minimal gitignore-style matcher inline (~100
  lines of Python), (iii) fail-closed with a clear "install `pathspec`" message. Preference:
  **(ii)** — a small in-repo module — because it avoids any external dependency for the plugin.
  Draft the matcher to cover `*`, `**`, `?`, `[...]`, leading `/`, trailing `/`, and `#`
  comments; document what's *not* supported.
- **Prompt block placement.** Should the ignore-file contents go **before** or **after** the
  standing brief? Leaning *after* (brief first, then the "and here's what to skim on this
  repo" block reads naturally). Codex is trained to look through system-prompt-like content
  first; this preserves that.
- (Previously open: self-matching. **Resolved** — see Principle 3: the parser hard-codes an
  exemption for `reviewerAgent-ignore.md`, and the test suite enforces it.)
